---
name: meta-browser-post
description: Preview, publish once, and check a Facebook Page post, Instagram feed photo, or Threads post through the user's signed-in native desktop website. Use when the user wants browser publishing or a provider permalink.
---

Use the bundled local CLI for the requested site. It uses the native composer and requires no SosoAPI account. For a writing-only request, return the draft in chat. Open a composer when the user wants to preview it there or publish it.

Run `npm ci --ignore-scripts --no-audit --no-fund --prefix SKILL_DIR` if the driver is missing. `SKILL_DIR` is this skill's installed directory. The examples below use `meta-post` as shorthand for `node SKILL_DIR/scripts/meta-post.mjs`. Supply values as literal arguments, preserving quotes and newlines.

1. **Choose the destination.** Use `facebook` for a Page, `instagram` for one feed photo, or `threads` for a top-level post. Use the exact Page name or @handle. Ask once for any missing account, caption or image. Facebook and Threads accept text and an optional JPEG/PNG. Instagram needs one approved image. Keep private text and media outside the repository.
2. **Preview.** Pick one unique key for the user's intended post. Run `meta-post preview PLATFORM --account NAME --key KEY --text CAPTION` and add `--image FILE` for a photo. The preview checks the signed-in identity, keeps the caption and file local, and returns an intent ID. Reuse the same key to resume. If there is no browser, run `meta-post browser PLATFORM` in a separate terminal and leave it open. The user signs in and handles any 2FA directly with the provider. An existing Chrome debugging session can also be used on the configured loopback port.
3. **Handle a different layout.** Read the CLI's `state` and `next` first. If it needs the composer, use the visible native tab to open a fresh Page post, Instagram Create → Post, or Threads New thread. Inspect only the composer or account switcher. Use a screenshot for visual media review when needed. Refresh the small scoped view after a transition. A reply, an edit, an extra destination, a boost or someone else's draft needs a different decision. If a layout still cannot be verified, report the stopping point.
4. **Publish once.** An explicit request to post the exact content, image and destination now supplies approval. If you drafted the caption, changed the media, or the user asked for review first, show the final combination and wait. Run `meta-post publish --id ID` only for that approved intent. This step uploads the image, prepares the caption and clicks the final native control. Keep one intent per destination.
5. **Return the result.** `published` means the native site reported success or the post detail was verified. Return its `url` when available. For `pending`, use `meta-post status --id ID`. If the user or the browser shows the new post, pass that actual permalink with `--url URL`. Never construct a URL or start another intent to retry an uncertain click. A confirmed post can temporarily have no verified link.

If the user explicitly prefers the official SosoAPI API, use the separately installed SosoAPI CLI and the intended connected workspace. That route requires SosoAPI login. After any uncertain native submission, resolve the original result before switching routes. The published Threads benchmark covers its recorded CLI/browser pair; this helper's token savings require a separate matched run.
